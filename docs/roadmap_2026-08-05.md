## The ceiling argument

Ten things were measured against retrieval accuracy this session. Two
helped. Both were **data plumbing, not modelling**:

| change | result | kind |
|---|---:|---|
| gallery cap 2 → 6 images/product | **+5.97pt** | used data we already had |
| K 150 → 400 (12-brand) | **+4.60pt** | used candidates we already had |
| patch rerank | −30pt | model idea |
| score fusion | −6.2pt | model idea |
| ArcFace vs SupCon | −13.4pt | model idea |
| brand boost (OCR) | +0.10pt | model idea |
| attribute-head rerank | ~0 (±0.5) | model idea |
| category gate | net-negative ×7 | model idea |
| distractor margin | 0.00pt | model idea |
| K past 150 *on the 6-brand catalog* | +0.08pt | exhausted |

**Six model ideas lost, one tied, and the two wins were both "stop
throwing away data you already have."** That is a strong signal about
where the remaining headroom is, and it matches the intuition in the
brief: what will make the difference is more data.

Two further pieces of evidence point the same way:

1. **The attribute oracle.** A perfect attribute head is worth **+8.4pt**
   R@1, consistently across seeds. The real head, at 67–85% per-facet
   accuracy, is worth ~0. The signal is real; the labels are the limit —
   and those labels are LLM-generated from product text, not measured.
2. **Frozen base SigLIP2 matches the fine-tuned v3 on attributes to
   within ~1pt.** The fine-tune added almost nothing there. The encoders
   are not obviously the constraint.

### So: what is actually left on accuracy

**Not exhausted, and worth doing:**

- **More images per product.** The gallery-cap result is the cleanest win
  of the session and it came purely from using 6 views instead of 2. The
  median product has 5. Scraping *more views per existing product* is
  likely worth more than more products.
- **More products hurts before it helps.** Doubling the catalog cost
  −16.9pt R@1 (59.92 → 43.05 at fixed K) because distractors grew. Growth
  needs K and an ANN index to scale with it, or accuracy goes backwards.
- **Human-labelled attributes.** The oracle says +8.4pt is sitting there.
  The blocker is label quality, which is a data-collection problem.
- **Better outfit detection** — just landed, 1.53 → 2.48 items/photo at
  48% → 91% precision. That improves the outfit side, not catalog R@1.

**Effectively exhausted:**

- Reranking ideas that re-weight what DINOv3 already encodes. Four
  attempts, four failures, mechanism understood each time.
- The category gate. Seven independent measurements.
- Loss-function changes at this data scale (1,077 identities × ~4.5
  images cannot estimate per-class centroids).

### The honest recommendation

**Start the production UI/UX track now, in parallel — do not wait.**

The reasons are concrete rather than defeatist:

- The end-to-end path already works and is fast enough (~1.5s warm).
- Every remaining accuracy lever is either *data collection* (slow,
  parallelisable, doesn't block UI) or *scaling infrastructure* (ANN
  index, also doesn't block UI).
- The largest single product failure this session was **not** model
  accuracy — it was that Dickies wasn't in the deployed catalog, so a
  Dickies photo confidently returned a Nike product. That is a data/ops
  bug, and fixing it fixed the behaviour completely.
- Real usage will surface the next real bottleneck faster than another
  offline experiment will. We currently have zero observations of a human
  using this.

Model work should continue — but as a background track measured against
a stable UI, not as the thing gating a first release.
